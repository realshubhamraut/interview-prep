SQL Terminology & Key Concepts¶

Understanding these foundational terms is essential before writing any SQL. A relational database stores data in tables (relations) with rows (tuples) and columns (attributes). Tables are linked through keys.

Core Database Terms¶

Term Meaning Example
Database Organized collection of structured data CREATE DATABASE company;
Schema Logical namespace grouping tables/views CREATE SCHEMA hr; — PG supports multiple schemas
Table (Relation) Collection of rows and columns CREATE TABLE employees (...);
Row (Record/Tuple) Single entry in a table One employee's complete data
Column (Field/Attribute) A specific property with a data type name VARCHAR(100)
Primary Key (PK) Unique + NOT NULL identifier for each row id SERIAL PRIMARY KEY
Foreign Key (FK) Column referencing PK of another table dept_id INT REFERENCES departments(id)
Candidate Key Column(s) that could be PK (unique + not null) email, phone if both unique

Index Data structure for faster SELECT queries CREATE INDEX idx_name ON emp(name);
View Virtual table from a saved query CREATE VIEW active_emp AS SELECT ...
Materialized View Cached view stored on disk (PG) Needs REFRESH to update
Stored Procedure Reusable block of SQL logic CREATE PROCEDURE process_order(...)
Function Returns a value; usable inside SELECT CREATE FUNCTION get_tax(...) RETURNS ...
Trigger Auto-executes on INSERT/UPDATE/DELETE Audit logging, timestamp updates
Transaction Group of operations — all succeed or all fail BEGIN; ... COMMIT; or ROLLBACK;
Sequence Auto-incrementing number generator (PG) CREATE SEQUENCE emp_id_seq;
Constraint Rule enforced on column data NOT NULL, UNIQUE, CHECK, FK
Normalization Organizing data to reduce redundancy 1NF → 2NF → 3NF → BCNF

Interview Knowledge Tables¶

Query Execution Order¶

SQL does NOT execute in the order you write it. Understanding this is critical for debugging.

Step Clause What happens Why it matters
1 FROM / JOIN Tables are loaded and joined Tables must exist
2 WHERE Rows filtered (before grouping) Can't use aliases or aggregates here
3 GROUP BY Rows grouped Non-aggregated columns must be in GROUP BY
4 HAVING Groups filtered (after grouping) Can use aggregates like HAVING COUNT(*) > 5
5 SELECT Columns/expressions computed Aliases created here
6 DISTINCT Duplicate rows removed Applied after SELECT
7 ORDER BY Results sorted Can use aliases (SELECT ran first)
8 LIMIT / OFFSET Results paginated Last step

JOINs Comparison¶

JOIN Type Returns NULL behavior Use case
INNER JOIN Only matching rows from both No NULLs from join Default join; most common
LEFT JOIN All left + matching right Right side NULLs if no match Find all items, even unmatched
RIGHT JOIN All right + matching left Left side NULLs if no match Rarely used (rewrite as LEFT)
FULL OUTER JOIN All from both sides Either side can be NULL Find all unmatched from both
CROSS JOIN Cartesian product No NULLs; n × m rows Generate combinations
SELF JOIN Table with itself Depends on join type Hierarchies, row comparisons
LATERAL JOIN Subquery references outer PG only Correlated subquery in FROM

Key pattern: LEFT JOIN + WHERE right.id IS NULL = anti-join (rows with NO match)

Database Basics & DDL (Data Definition Language)¶

DDL commands define and modify the structure of database objects — tables, schemas, indexes. These changes are auto-committed (cannot be rolled back in most databases).

CREATE TABLE¶

Tables are the foundation of a relational database. Each column has a name, data type, and optional constraints.

How Window Functions Work — Visual¶

Data:
+------+-------+--------+
| dept | name  | salary |
+------+-------+--------+
| Eng  | Alice |  80000 |
| Eng  | Bob   |  75000 |
| Eng  | Carol |  80000 |
| HR   | Dave  |  60000 |
| HR   | Eve   |  65000 |
+------+-------+--------+

ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC):
  Each dept is a separate "window"

  Window: Eng                    Window: HR
  +-------+--------+-----+      +------+--------+-----+
  | Alice |  80000 |  1  |      | Eve  |  65000 |  1  |
  | Carol |  80000 |  2  |      | Dave |  60000 |  2  |
  | Bob   |  75000 |  3  |      +------+--------+-----+
  +-------+--------+-----+

RANK() vs DENSE_RANK() vs ROW_NUMBER():
  +-------+--------+-----+------+------------+
  | name  | salary | ROW | RANK | DENSE_RANK |
  +-------+--------+-----+------+------------+
  | Alice |  80000 |  1  |   1  |     1      |

Window Frame (ROWS BETWEEN):

Current row = Bob (row 3)

ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW:
  [Alice, Carol, >>Bob<<]  => running total up to current row

ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING:
  [Carol, >>Bob<<, next]   => 3-row moving average

ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING:
  [all rows in partition]  => total for partition

How Recursive CTEs Work — Step by Step¶

WITH RECURSIVE org_chart AS (
    -- ANCHOR: Start with the CEO (no manager)
    SELECT id, name, manager_id, 1 AS level
    FROM employees WHERE manager_id IS NULL

    UNION ALL

    -- RECURSIVE: Find employees whose manager is already in the result
    SELECT e.id, e.name, e.manager_id, oc.level + 1
    FROM employees e
    JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT * FROM org_chart;

Execution — iteration by iteration:

ITERATION 0 (Anchor):
+----+---------+--------+-------+
| id |  name   | mgr_id | level |
+----+---------+--------+-------+
|  1 | Alice   |  NULL  |   1   |   <-- CEO (no manager)
+----+---------+--------+-------+

ITERATION 1 (Recursive — find reports of Alice):
+----+---------+--------+-------+
|  2 | Bob     |    1   |   2   |   <-- Reports to Alice
|  3 | Carol   |    1   |   2   |   <-- Reports to Alice
+----+---------+--------+-------+

ITERATION 2 (Recursive — find reports of Bob, Carol):
+----+---------+--------+-------+
|  4 | Dave    |    2   |   3   |   <-- Reports to Bob
|  5 | Eve     |    3   |   3   |   <-- Reports to Carol
+----+---------+--------+-------+

ITERATION 3: No more employees found => STOP

FINAL RESULT (UNION ALL of all iterations):
+----+---------+--------+-------+
| id |  name   | mgr_id | level |
+----+---------+--------+-------+
|  1 | Alice   |  NULL  |   1   |
|  2 | Bob     |    1   |   2   |
|  3 | Carol   |    1   |   2   |
|  4 | Dave    |    2   |   3   |
|  5 | Eve     |    3   |   3   |
+----+---------+--------+-------+

As a tree:

          Alice (CEO)
          /         \
       Bob          Carol
       /               \
    Dave               Eve

Recursive CTE — key rules:

  • Must have ANCHOR (non-recursive) + RECURSIVE (self-referencing) parts
  • Connected by UNION ALL (or UNION to remove duplicates)
  • Terminates when recursive part returns zero rows
  • Always add a depth limit (WHERE level < 10) to prevent infinite loops

ALTER TABLE¶

Modify existing table structure without dropping and recreating.

-- Add column
ALTER TABLE students ADD COLUMN nationality VARCHAR(50) DEFAULT 'Indian';

-- Drop column
ALTER TABLE students DROP COLUMN nationality;

-- Rename column (MySQL)
ALTER TABLE students CHANGE COLUMN nationality country VARCHAR(50);
-- Rename column (PostgreSQL)
ALTER TABLE students RENAME COLUMN nationality TO country;

-- Change data type
ALTER TABLE employees ALTER COLUMN salary TYPE NUMERIC(12, 2);
-- MySQL: ALTER TABLE employees MODIFY COLUMN salary DECIMAL(12,2);

-- Add constraint
ALTER TABLE students ADD CONSTRAINT chk_cgpa CHECK (cgpa >= 0 AND cgpa <= 10);

-- Drop constraint
ALTER TABLE students DROP CONSTRAINT chk_cgpa;

-- Rename table
ALTER TABLE employees RENAME TO staff;

DROP, TRUNCATE, DELETE — Differences¶

-- DROP: removes entire table structure + data (IRREVERSIBLE)
DROP TABLE IF EXISTS temp_table;
DROP TABLE employees CASCADE;  -- also removes dependent FK references

-- TRUNCATE: removes all data, keeps structure (faster than DELETE)
TRUNCATE TABLE employees;
TRUNCATE TABLE employees RESTART IDENTITY CASCADE;  -- reset SERIAL

-- DELETE: removes specific rows, fully logged, can be rolled back
DELETE FROM employees WHERE is_active = FALSE;

-- MySQL: DESCRIBE students;  or  SHOW CREATE TABLE students;
-- PostgreSQL: \d students  (in psql)

Data Manipulation — INSERT, UPDATE, DELETE¶

DML commands modify the data inside tables. Unlike DDL, DML operations can be rolled back within a transaction.

INSERT¶

-- Single row
INSERT INTO departments (department_name, hod_name, office_location, budget)
VALUES ('Computer Science', 'Dr. Rajesh Kumar', 'Block A', 5000000.00);

-- Multiple rows
INSERT INTO students (first_name, last_name, email, cgpa, gender) VALUES
    ('Rahul', 'Sharma', 'rahul@example.com', 8.5, 'Male'),
    ('Priya', 'Patel', 'priya@example.com', 9.2, 'Female'),
    ('Amit', 'Kumar', 'amit@example.com', 7.8, 'Male');

-- Insert from SELECT (copy data between tables)
INSERT INTO emp_archive
SELECT * FROM employees WHERE is_active = FALSE;

-- UPSERT: Insert or Update on conflict (PostgreSQL)
INSERT INTO employees (email, first_name, salary)
VALUES ('rahul@example.com', 'Rahul', 80000)
ON CONFLICT (email) DO UPDATE SET salary = EXCLUDED.salary;

-- MySQL equivalent: ON DUPLICATE KEY UPDATE
INSERT INTO employees (email, first_name, salary)
VALUES ('rahul@example.com', 'Rahul', 80000)
ON DUPLICATE KEY UPDATE salary = VALUES(salary);

-- RETURNING clause (PostgreSQL) — get inserted data back
INSERT INTO employees (first_name, last_name, email)
VALUES ('New', 'Employee', 'new@example.com')
RETURNING id, first_name, email;

UPDATE¶

-- Simple update
UPDATE students SET phone = '9999999999' WHERE student_id = 1;

-- Update multiple columns
UPDATE students SET cgpa = 9.0, address = 'Mumbai' WHERE student_id = 1;

-- Update with calculation
UPDATE students SET cgpa = cgpa + 0.5 WHERE cgpa < 8.0;

-- Update with JOIN (PostgreSQL)
UPDATE employees e SET salary = salary + d.budget * 0.01
FROM departments d WHERE e.dept_id = d.id AND d.name = 'Sales';

-- Update with JOIN (MySQL)
UPDATE courses c JOIN departments d ON c.department_id = d.department_id
SET c.is_active = FALSE
WHERE d.department_name = 'Database Management';

-- Update with subquery
UPDATE students SET cgpa = (
    SELECT AVG(CASE
        WHEN e.grade='A+' THEN 10 WHEN e.grade='A' THEN 9
        WHEN e.grade='B+' THEN 8 WHEN e.grade='B' THEN 7 ELSE 5
    END) FROM enrollments e WHERE e.student_id = students.student_id
) WHERE student_id IN (SELECT student_id FROM enrollments);

DELETE¶

-- Delete specific rows
DELETE FROM students WHERE first_name = 'Test';

-- Delete with JOIN (MySQL)
DELETE c FROM courses c
JOIN departments d ON c.department_id = d.department_id
WHERE c.course_code = 'TEST101';

-- Delete with subquery
DELETE FROM enrollments
WHERE grade = 'F' AND student_id IN (
    SELECT student_id FROM students WHERE cgpa > 8.0
);

-- Delete with RETURNING (PostgreSQL)
DELETE FROM employees WHERE id = 10 RETURNING *;

SELECT & Filtering¶

The SELECT statement is the most used SQL command. It retrieves data from tables with filtering, sorting, and pagination.

Basic SELECT¶

-- All columns
SELECT * FROM students;

-- Specific columns
SELECT first_name, last_name, email, cgpa FROM students;

-- Aliases
SELECT first_name AS "First Name", salary * 12 AS annual_salary FROM employees;

-- DISTINCT
SELECT DISTINCT gender FROM students;

-- DISTINCT ON (PostgreSQL only) — first row per group
SELECT DISTINCT ON (dept_id) * FROM employees
ORDER BY dept_id, salary DESC;

WHERE Clause & Operators¶

Filter rows using conditions. WHERE is applied before grouping.

-- Comparison
SELECT * FROM students WHERE cgpa > 8.5;
SELECT * FROM students WHERE date_of_birth >= '2000-01-01';

-- BETWEEN (inclusive both ends)
SELECT * FROM students WHERE cgpa BETWEEN 8.0 AND 9.0;

-- IN / NOT IN
SELECT * FROM students WHERE student_id IN (1, 3, 5);

-- LIKE pattern matching
-- % = any characters, _ = exactly one character
SELECT * FROM students WHERE first_name LIKE 'A%';      -- starts with A
SELECT * FROM students WHERE email LIKE '%@gmail.com';   -- ends with @gmail.com
SELECT * FROM students WHERE last_name LIKE 'S_____';    -- S + exactly 5 chars

-- ILIKE (case-insensitive, PostgreSQL only)
SELECT * FROM employees WHERE first_name ILIKE 'john%';

-- NULL checks (never use = NULL)
SELECT * FROM students WHERE phone IS NULL;
SELECT * FROM students WHERE phone IS NOT NULL;

-- AND / OR / NOT
SELECT * FROM students
WHERE (dept_id = 1 OR dept_id = 2) AND salary > 50000;

-- EXISTS (check if subquery returns any rows)
SELECT * FROM departments d
WHERE EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.id);

ORDER BY, LIMIT, OFFSET¶

-- Sort ascending/descending
SELECT * FROM students ORDER BY cgpa DESC;
SELECT * FROM students ORDER BY last_name ASC, first_name ASC;

-- NULLS FIRST / NULLS LAST (PostgreSQL)
SELECT * FROM employees ORDER BY phone NULLS LAST;

-- Pagination with LIMIT/OFFSET
SELECT * FROM students ORDER BY student_id LIMIT 10;           -- first 10
SELECT * FROM students ORDER BY student_id LIMIT 10 OFFSET 20; -- rows 21-30

-- SQL standard: FETCH
SELECT * FROM employees ORDER BY id FETCH FIRST 10 ROWS ONLY;

Aggregate Functions & GROUP BY¶

Aggregate functions compute a single result from multiple rows. GROUP BY groups rows before aggregation; HAVING filters the resulting groups.

-- Basic aggregates
SELECT
    COUNT(*) AS total_students,
    AVG(cgpa) AS average_cgpa,
    MIN(cgpa) AS lowest,
    MAX(cgpa) AS highest
FROM students;

-- COUNT non-NULL vs COUNT(*)
SELECT COUNT(date_of_birth) AS has_dob FROM students; -- excludes NULLs
SELECT COUNT(*) AS total FROM students;               -- includes NULLs

-- GROUP BY
SELECT gender, COUNT(*) AS count, AVG(cgpa) AS avg_cgpa
FROM students GROUP BY gender;

-- GROUP BY with JOIN
SELECT d.department_name, COUNT(c.course_id) AS courses, SUM(c.credits) AS total_credits
FROM departments d LEFT JOIN courses c ON d.department_id = c.department_id
GROUP BY d.department_name ORDER BY courses DESC;

HAVING — Filter Groups¶

WHERE filters rows before grouping. HAVING filters groups after aggregation.

-- Departments with more than 1 course
SELECT department_id, COUNT(*) AS course_count
FROM courses GROUP BY department_id HAVING COUNT(*) > 1;

-- STRING_AGG / GROUP_CONCAT
-- PostgreSQL:
SELECT dept_id, STRING_AGG(first_name, ', ' ORDER BY first_name) AS members
FROM employees GROUP BY dept_id;
-- MySQL:
SELECT dept_id, GROUP_CONCAT(first_name ORDER BY first_name SEPARATOR ', ') AS members
FROM employees GROUP BY dept_id;

-- ROLLUP (subtotals + grand total)
SELECT dept_id, EXTRACT(YEAR FROM hire_date) AS yr, COUNT(*)
FROM employees GROUP BY ROLLUP(dept_id, EXTRACT(YEAR FROM hire_date));

-- Conditional aggregation with CASE
SELECT
    COUNT(*) AS total,
    COUNT(CASE WHEN gender='Male' THEN 1 END) AS male_count,
    COUNT(CASE WHEN gender='Female' THEN 1 END) AS female_count,
    AVG(CASE WHEN gender='Male' THEN cgpa END) AS male_avg
FROM students;

JOINs — All Types¶

JOINs combine rows from two or more tables based on related columns (usually FK→PK). The type of JOIN determines what happens with unmatched rows.

INNER JOIN¶

Returns only rows with a match in both tables.

SELECT s.first_name, s.last_name, c.course_name, e.grade
FROM students s
INNER JOIN enrollments e ON s.student_id = e.student_id
INNER JOIN courses c ON e.course_id = c.course_id;

LEFT JOIN (LEFT OUTER JOIN)¶

All rows from left + matching right. NULLs where no match on right.

-- All students, even those not enrolled in any course
SELECT s.first_name, c.course_name, e.grade
FROM students s
LEFT JOIN enrollments e ON s.student_id = e.student_id
LEFT JOIN courses c ON e.course_id = c.course_id;

-- Anti-join: find students NOT enrolled anywhere
SELECT s.first_name FROM students s
LEFT JOIN enrollments e ON s.student_id = e.student_id
WHERE e.student_id IS NULL;

RIGHT JOIN, FULL OUTER JOIN, CROSS JOIN¶

-- RIGHT JOIN: all courses, even those with no enrollments
SELECT c.course_name, e.student_id
FROM enrollments e RIGHT JOIN courses c ON e.course_id = c.course_id;

-- FULL OUTER JOIN (PostgreSQL; MySQL uses UNION trick)
SELECT e.first_name, d.name FROM employees e
FULL OUTER JOIN departments d ON e.dept_id = d.id;

-- MySQL FULL JOIN workaround:
SELECT s.first_name, c.course_name
FROM students s LEFT JOIN enrollments e ON s.student_id = e.student_id
LEFT JOIN courses c ON e.course_id = c.course_id
UNION
SELECT s.first_name, c.course_name
FROM students s RIGHT JOIN enrollments e ON s.student_id = e.student_id
RIGHT JOIN courses c ON e.course_id = c.course_id
WHERE s.student_id IS NULL;

-- CROSS JOIN: every combination (cartesian product)
SELECT s.first_name, c.course_name
FROM students s CROSS JOIN courses c LIMIT 10;

SELF JOIN¶

A table joined with itself. Common for hierarchical data (employee→manager) and row comparisons.

Subqueries & CTEs¶

Subqueries are queries nested inside other queries. CTEs (Common Table Expressions) use WITH to create named temporary result sets, making complex queries readable.

Subqueries¶

-- Scalar subquery (single value)
SELECT first_name, cgpa FROM students
WHERE cgpa > (SELECT AVG(cgpa) FROM students);

-- IN subquery
SELECT course_code, course_name FROM courses
WHERE course_id IN (SELECT course_id FROM enrollments WHERE student_id = 1);

-- Derived table (subquery in FROM)
SELECT gender, average_cgpa FROM (
    SELECT gender, AVG(cgpa) AS average_cgpa FROM students GROUP BY gender
) sub WHERE average_cgpa > 8.0;

-- EXISTS (correlated subquery — usually faster than IN)
SELECT s.first_name FROM students s
WHERE EXISTS (
    SELECT 1 FROM enrollments e
    WHERE e.student_id = s.student_id AND e.grade = 'A+'
);

-- Subquery in SELECT
SELECT d.department_name,
    (SELECT COUNT(*) FROM courses c WHERE c.department_id = d.department_id) AS course_count
FROM departments d;

How Subqueries Execute — Step by Step¶

Scalar Subquery (returns single value):

SELECT name, salary FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

Execution:
  Step 1: Inner query runs FIRST
          SELECT AVG(salary) FROM employees  =>  55000

  Step 2: Outer query uses the result
          SELECT name, salary FROM employees
          WHERE salary > 55000

Correlated Subquery (runs ONCE PER outer row):

SELECT e.name, e.salary FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees e2
                  WHERE e2.dept_id = e.dept_id);

Execution:
  For EACH row in outer table:
    Row 1 (Alice, dept=1):  inner runs for dept=1  =>  avg=60k  =>  compare
    Row 2 (Bob,   dept=2):  inner runs for dept=2  =>  avg=50k  =>  compare
    Row 3 (Carol, dept=1):  inner runs for dept=1  =>  avg=60k  =>  compare
    ...
  Very slow on large tables! Consider rewriting as JOIN.

EXISTS subquery (checks if rows exist — stops at first match):

SELECT name FROM departments d
WHERE EXISTS (SELECT 1 FROM employees e WHERE e.dept_id = d.id);

Execution:
  For each department:
    dept 'Engineering':  any employees? => YES => include
    dept 'Archived':     any employees? => NO  => skip
    (stops scanning as soon as first match found — efficient)

CTEs (WITH clause)¶

CTEs break complex queries into named, readable steps. Each CTE is like a temporary view for that query.

-- Basic CTE
WITH StudentGrades AS (
    SELECT s.first_name, s.last_name, e.grade, c.course_name
    FROM students s
    JOIN enrollments e ON s.student_id = e.student_id
    JOIN courses c ON e.course_id = c.course_id
)
SELECT * FROM StudentGrades WHERE grade = 'A';

-- Multiple CTEs
WITH
DeptCourses AS (
    SELECT department_id, COUNT(*) AS course_count
    FROM courses GROUP BY department_id
),
TopDepts AS (
    SELECT * FROM DeptCourses WHERE course_count > 1
)
SELECT d.department_name, td.course_count
FROM TopDepts td JOIN departments d ON td.department_id = d.department_id;

Recursive CTEs¶

Used for hierarchical / tree data like org charts, category trees, and sequences.

-- Employee hierarchy (org chart)
WITH RECURSIVE EmployeeHierarchy AS (
    -- Base: top-level managers (no manager)
    SELECT employee_id, first_name, manager_id, 0 AS level,
        CONCAT(first_name, ' ', last_name) AS path
    FROM employees WHERE manager_id IS NULL
    
    UNION ALL
    
    -- Recursive: each level of reports
    SELECT e.employee_id, e.first_name, e.manager_id, eh.level + 1,
        CONCAT(eh.path, ' > ', e.first_name, ' ', e.last_name)
    FROM employees e
    JOIN EmployeeHierarchy eh ON e.manager_id = eh.employee_id
)
SELECT * FROM EmployeeHierarchy ORDER BY level, first_name;

-- Generate date series (MySQL, since no GENERATE_SERIES)
WITH RECURSIVE DateSeries AS (
    SELECT CURDATE() AS dt
    UNION ALL
    SELECT dt + INTERVAL 1 DAY FROM DateSeries WHERE dt < CURDATE() + INTERVAL 6 DAY
)
SELECT dt, DAYNAME(dt) AS day_of_week FROM DateSeries;

Window Functions¶

Window functions perform calculations across a set of rows related to the current row, without collapsing rows into groups. They use the OVER() clause.

Syntax: function() OVER (PARTITION BY ... ORDER BY ... frame_clause)

Ranking Functions¶

-- ROW_NUMBER, RANK, DENSE_RANK: from course sales table
SELECT product_name, category, amount,
    ROW_NUMBER() OVER(ORDER BY amount DESC) AS row_num,
    RANK()       OVER(ORDER BY amount DESC) AS rank,
    DENSE_RANK() OVER(ORDER BY amount DESC) AS dense_rank
FROM sales;

-- Top N per group (INTERVIEW FAVORITE)
WITH ranked AS (
    SELECT *, DENSE_RANK() OVER (
        PARTITION BY dept_id ORDER BY salary DESC
    ) AS rn
    FROM employees
)
SELECT * FROM ranked WHERE rn <= 3;

-- NTILE: divide into quartiles
SELECT first_name, salary, NTILE(4) OVER (ORDER BY salary) AS quartile
FROM employees;

LAG, LEAD — Compare with Previous/Next Row¶

-- Previous and next values
SELECT product_name, sale_date, amount,
    LAG(amount, 1)  OVER (ORDER BY sale_date) AS prev_amount,
    LEAD(amount, 1) OVER (ORDER BY sale_date) AS next_amount,
    amount - LAG(amount, 1) OVER (ORDER BY sale_date) AS diff
FROM sales;

-- Year-over-year revenue growth
WITH yearly AS (
    SELECT EXTRACT(YEAR FROM order_date) AS yr, SUM(amount) AS revenue
    FROM orders GROUP BY 1
)
SELECT yr, revenue,
    LAG(revenue) OVER (ORDER BY yr) AS prev_year,
    ROUND((revenue - LAG(revenue) OVER (ORDER BY yr))
        / LAG(revenue) OVER (ORDER BY yr) * 100, 2) AS growth_pct
FROM yearly;

Running Totals & Moving Averages¶

-- Cumulative/running total
SELECT sale_date, amount,
    SUM(amount) OVER (ORDER BY sale_date) AS running_total
FROM sales;

-- Per-category running total
SELECT category, sale_date, amount,
    SUM(amount) OVER (PARTITION BY category ORDER BY sale_date) AS cat_running
FROM sales;

-- 3-period moving average
SELECT sale_date, amount,
    AVG(amount) OVER (ORDER BY sale_date ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING) AS moving_avg
FROM sales;

-- Percentage of total
SELECT first_name, salary,
    ROUND(salary * 100.0 / SUM(salary) OVER (), 2) AS pct_of_total,
    ROUND(salary * 100.0 / SUM(salary) OVER (PARTITION BY dept_id), 2) AS pct_of_dept
FROM employees;

Set Operations¶

Set operations combine results from two or more SELECT statements. Both queries must have the same number of columns with compatible types.

-- UNION: combine + remove duplicates
SELECT email FROM employees UNION SELECT email FROM contractors;

-- UNION ALL: combine + keep duplicates (faster, no sort needed)
SELECT email FROM employees UNION ALL SELECT email FROM contractors;

-- INTERSECT: rows in BOTH
SELECT email FROM employees INTERSECT SELECT email FROM newsletter;

-- EXCEPT: rows in first but NOT second
SELECT email FROM employees EXCEPT SELECT email FROM terminated;

-- Note: MySQL uses UNION but not INTERSECT/EXCEPT until MySQL 8.0.31+

Views and Materialized Views¶

What is a View?¶

A view is a named, stored SQL query that acts as a virtual table. It does not store data — every time you query a view, the database re-executes the underlying SQL statement and returns the live result.

Think of a view as a "saved query with a name." It simplifies complex queries, enforces security (expose only certain columns/rows), and provides a stable interface even when underlying tables change.

How Views Work Internally¶

User queries: SELECT * FROM my_view WHERE x > 10

Database rewrites to: SELECT ... FROM (original_view_query) WHERE x > 10

This process is called "view expansion" or "query rewriting"

The optimizer merges the view query with the outer query into a single execution plan — it does NOT run two separate queries. This is why simple views have virtually zero performance overhead.

Updatable Views — Rules¶

A view is automatically updatable (per SQL standard) when:

  • It selects from exactly one table
  • It does not use GROUP BY, HAVING, DISTINCT, UNION, or aggregate functions
  • It does not use window functions
  • Every column maps to an actual table column (no expressions)

PostgreSQL is more permissive: it allows creating INSTEAD OF triggers to make any view updatable.

WITH CHECK OPTION¶

Prevents INSERT/UPDATE through a view that would make the row invisible to the view:

CREATE VIEW active_students AS
SELECT * FROM students WHERE is_active = TRUE
WITH CHECK OPTION;

-- This will FAIL because is_active=FALSE would disappear from the view:
INSERT INTO active_students (name, is_active) VALUES ('Ghost', FALSE);
-- ERROR: new row violates check option for view "active_students"
  • LOCAL: Only checks the current view's WHERE clause
  • CASCADED (default): Checks this view AND any underlying views

Materialized Views (PostgreSQL Only)¶

A materialized view stores the query result on disk like a real table. It is a snapshot — data becomes stale until you manually refresh it.

Feature Regular View Materialized View

Indexable? No Yes (create indexes on it)

How Views Work — Query Rewriting¶

STEP 1: You create a view:

  CREATE VIEW high_earners AS
  SELECT name, salary, dept FROM employees WHERE salary > 80000;

  (Nothing is stored except the query definition)

STEP 2: You query the view:

  SELECT name, dept FROM high_earners WHERE dept = 'Engineering';

STEP 3: Database REWRITES your query (view expansion):

  SELECT name, dept FROM (
    SELECT name, salary, dept FROM employees WHERE salary > 80000
  ) AS high_earners
  WHERE dept = 'Engineering';

STEP 4: Optimizer MERGES into a single efficient query:

  SELECT name, dept FROM employees
  WHERE salary > 80000 AND dept = 'Engineering';

  (Uses indexes on salary and dept — same performance as direct query!)

Indexes and Performance — Deep Dive¶

What is an Index?¶

An index is a separate data structure that maintains a sorted/organized copy of specific column values along with pointers to the actual table rows. It speeds up reads (SELECT, WHERE, JOIN, ORDER BY) at the cost of slower writes (INSERT, UPDATE, DELETE must also update the index) and extra storage.

Analogy: A book index maps topics to page numbers. Without it, you scan every page (full table scan). With it, you jump directly to the relevant page (index seek).

How Indexes Work Internally¶

B-Tree Index (default in PostgreSQL and MySQL):

                    [50]
                   /    \
             [20, 35]   [65, 80]
            /   |   \   /   |   \
         [10] [25] [40] [55] [70] [90]
          |    |    |    |    |    |
         ptr  ptr  ptr  ptr  ptr  ptr  -> actual table rows
  • Balanced tree structure; all leaf nodes at same depth
  • $O(\log n)$ lookup time (e.g., 1 billion rows = only about 30 comparisons)
  • Leaf nodes are linked (doubly-linked list) for efficient range scans
  • Supports: =, <, >, <=, >=, BETWEEN, LIKE 'abc%' (prefix), IS NULL, ORDER BY

How Clustered vs Non-Clustered (Heap) Storage Differ¶

MySQL InnoDB (Clustered):

  • Table data is stored in primary key order (the PK IS the table)
  • Secondary indexes store PK value -> requires double lookup
  • Choosing a good PK matters a lot (auto-increment INT is ideal)

PostgreSQL (Heap):

  • Table data stored in insertion order (heap); no inherent order
  • All indexes (including PK) point to physical location (ctid)
  • CLUSTER table USING index_name; physically reorders once (not maintained)
  • No double-lookup penalty for secondary indexes

Composite (Multi-Column) Index and the Leftmost Prefix Rule¶

CREATE INDEX idx_dept_sal_name ON employees(dept_id, salary, last_name);

This index helps queries that filter on leftmost prefix of columns:

Query WHERE clause Uses index? Why
dept_id = 5 Yes Leftmost column
dept_id = 5 AND salary > 50000 Yes First two columns
dept_id = 5 AND salary > 50000 AND last_name = 'Smith' Yes All three columns
salary > 50000 No Skipped leftmost column
last_name = 'Smith' No Skipped first two columns
dept_id = 5 AND last_name = 'Smith' Partial Uses dept_id; skips salary; may scan name

Rule of thumb: Put the most selective (highest cardinality) column first, or the column used most often in equality conditions.

Special Index Types — When to Use¶

Partial Index (PostgreSQL only):

CREATE INDEX idx_active_orders ON orders(customer_id) WHERE status = 'active';
-- Index is MUCH smaller since it only includes active orders
-- Perfect when you mostly query active records

Expression / Functional Index:

CREATE INDEX idx_lower_email ON users(LOWER(email));
-- Now this query uses the index:
SELECT * FROM users WHERE LOWER(email) = 'john@example.com';

Covering Index with INCLUDE (PostgreSQL 11+):

CREATE INDEX idx_cover ON employees(dept_id) INCLUDE(first_name, salary);
-- Index-only scan: doesn't need to visit the table at all
-- INCLUDE columns are stored in leaf nodes but NOT used for searching

BRIN Index (PostgreSQL):

CREATE INDEX idx_ts ON logs USING BRIN(created_at);
-- Stores min/max per block range; extremely small
-- Only effective on physically ordered data (e.g., append-only log tables)
-- 1000x smaller than B-Tree for time-series data

Index-Only Scans¶

When ALL requested columns are in the index, the database can skip visiting the actual table entirely. This is dramatically faster for covered queries.

PostgreSQL: Uses the visibility map to check if all rows in a page are visible to all transactions. If yes, index-only scan; otherwise, must visit heap to check visibility.

MySQL InnoDB: A "covering index" achieves the same — if all columns in SELECT, WHERE, and ORDER BY are in the index, no primary key lookup needed.

When NOT to Index¶

Situation Why
Very small tables (<1000 rows) Full scan is faster than index lookup
Low-cardinality columns (gender: M/F) Index returns too many rows; sequential scan is better
Write-heavy tables with rare reads Index maintenance overhead hurts writes
Columns rarely used in WHERE/JOIN/ORDER Wasted storage and write overhead
Already indexed via primary key Redundant

B-Tree Index — How Lookup Works¶

Query: SELECT * FROM employees WHERE salary = 55000;

B-Tree for salary column:

                        [50000]
                       /       \
              [25000, 40000]   [65000, 80000]
             /    |     \      /    |     \
         [10k] [30k] [45k] [55k] [70k] [90k]   <-- Leaf nodes
           |     |     |     |     |     |           (sorted, linked)
          ptr   ptr   ptr   ptr   ptr   ptr
                             |
                    Found! Follow pointer
                    to actual table row

Steps: Root -> Right child -> Left leaf -> Found!
       Only 3 comparisons for millions of rows (O(log n))

Without index (Sequential Scan):

Scan EVERY row:  Row1 -> Row2 -> Row3 -> ... -> RowN
                 Check each: salary = 55000?
                 O(n) — must read entire table

Composite Index — Leftmost Prefix Rule:

Index: (dept_id, salary, name)

Think of it like a phone book sorted by:
  1. Last name (dept_id)
  2. First name (salary)
  3. Middle name (name)

Looking up "Smith"                    => YES (leftmost)
Looking up "Smith, John"              => YES (first two)
Looking up "Smith, John, Michael"     => YES (all three)
Looking up by first name "John" only  => NO! (skipped last name)
Looking up by middle name only        => NO! (skipped first two)

Partial Index — why it is smaller and faster:

Full index on status:           Partial index (WHERE status = 'active'):
+--------+-----+               +--------+-----+
| active | ptr |               | active | ptr |   <- Only 5% of rows!
| active | ptr |               | active | ptr |
| closed | ptr |               | active | ptr |
| closed | ptr |               +--------+-----+
| closed | ptr |
| closed | ptr |               95% smaller; 95% faster to update
| closed | ptr |
| active | ptr |
+--------+-----+

Index-Only Scan vs Index Scan:

CREATE INDEX idx ON emp(dept_id) INCLUDE(name, salary);

Index Scan:                     Index-Only Scan:
  Index                          Index (has name, salary too!)
    |                              |
  Find ptr                       Find data directly
    |                              |
  Go to table (heap)             Return result
    |                            (skip table entirely!)
  Read row
    |
  Return result

Triggers¶

Triggers automatically execute a function BEFORE or AFTER an INSERT, UPDATE, or DELETE. Common uses: audit logging, data validation, auto-updating timestamps.

-- MySQL: Audit trail triggers
CREATE TABLE student_audit (
    audit_id INT AUTO_INCREMENT PRIMARY KEY,
    student_id INT, action_type VARCHAR(10),
    action_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    old_data JSON, new_data JSON
);

DELIMITER //
CREATE TRIGGER after_student_insert AFTER INSERT ON students
FOR EACH ROW BEGIN
    INSERT INTO student_audit (student_id, action_type, new_data)
    VALUES (NEW.student_id, 'INSERT',
        JSON_OBJECT('first_name',NEW.first_name,'email',NEW.email,'cgpa',NEW.cgpa));
END //

CREATE TRIGGER after_student_update AFTER UPDATE ON students
FOR EACH ROW BEGIN
    INSERT INTO student_audit (student_id, action_type, old_data, new_data)
    VALUES (NEW.student_id, 'UPDATE',
        JSON_OBJECT('first_name',OLD.first_name,'cgpa',OLD.cgpa),
        JSON_OBJECT('first_name',NEW.first_name,'cgpa',NEW.cgpa));
END //

-- Validation trigger
CREATE TRIGGER before_enrollment_insert BEFORE INSERT ON enrollments
FOR EACH ROW BEGIN
    DECLARE cnt INT;
    SELECT COUNT(*) INTO cnt FROM enrollments WHERE student_id = NEW.student_id;
    IF cnt >= 5 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Student cannot enroll in more than 5 courses';
    END IF;
END //
DELIMITER ;

-- PostgreSQL: Audit trigger
CREATE OR REPLACE FUNCTION log_changes() RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit_log(tbl, action, new_data)
        VALUES (TG_TABLE_NAME, 'INSERT', row_to_json(NEW)::JSONB);
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit_log(tbl, action, old_data, new_data)
        VALUES (TG_TABLE_NAME, 'UPDATE',
            row_to_json(OLD)::JSONB, row_to_json(NEW)::JSONB);
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit_log(tbl, action, old_data)
        VALUES (TG_TABLE_NAME, 'DELETE', row_to_json(OLD)::JSONB);
        RETURN OLD;
    END IF;
END; $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit AFTER INSERT OR UPDATE OR DELETE ON employees
FOR EACH ROW EXECUTE FUNCTION log_changes();

Transactions & Concurrency¶

A transaction groups multiple SQL statements into a single atomic unit — either ALL succeed or ALL fail. PostgreSQL uses MVCC for concurrent access.

-- Basic transaction
BEGIN;  -- or START TRANSACTION (MySQL)
    UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
    UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT;  -- save all changes
-- ROLLBACK;  -- undo all changes

-- Savepoints (partial rollback)
BEGIN;
    INSERT INTO employees VALUES (...);  -- this stays
    SAVEPOINT sp1;
    INSERT INTO employees VALUES (...);  -- this might fail
    ROLLBACK TO sp1;  -- undo only second insert
COMMIT;  -- first insert is saved

-- MySQL: Transaction in procedure
DELIMITER //
CREATE PROCEDURE TransferStudent(IN sid INT, IN from_cid INT, IN to_cid INT)
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; END;
    START TRANSACTION;
    DELETE FROM enrollments WHERE student_id=sid AND course_id=from_cid;
    INSERT INTO enrollments (student_id, course_id) VALUES (sid, to_cid);
    COMMIT;
    SELECT 'Transfer successful' AS message;
END //
DELIMITER ;

-- Set isolation level
BEGIN ISOLATION LEVEL SERIALIZABLE;
    SELECT * FROM accounts WHERE id = 1;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- Row-level locking
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;  -- locks until COMMIT

-- SKIP LOCKED (job queue pattern)
SELECT * FROM jobs WHERE status = 'pending'
ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;

Advanced PostgreSQL — Arrays, JSON, Full-Text Search¶

PostgreSQL extends standard SQL with powerful data types and operators not found in most other databases.

Arrays¶

PostgreSQL supports array columns — store multiple values in a single field. Arrays are 1-indexed.

CREATE TABLE students_pg (
    id SERIAL PRIMARY KEY, name TEXT,
    scores INTEGER[]
);
INSERT INTO students_pg (name, scores) VALUES
    ('Alice', '{90, 85, 95}'), ('Bob', ARRAY[75, 80, 70]);

-- Access (1-indexed!)
SELECT name, scores[1] AS first_score FROM students_pg;

-- Array functions
SELECT name, array_length(scores,1) AS n,
    array_to_string(scores, ', ') AS s FROM students_pg;

-- ANY / ALL
SELECT * FROM students_pg WHERE 90 = ANY(scores);
SELECT * FROM students_pg WHERE 70 < ALL(scores);

-- Unnest: expand to rows
SELECT name, unnest(scores) AS score FROM students_pg;

-- Aggregate into array
SELECT dept_id, ARRAY_AGG(first_name ORDER BY first_name) FROM employees GROUP BY dept_id;

JSONB¶

JSONB stores JSON in a binary format that supports indexing and efficient querying. Always prefer JSONB over JSON.

CREATE TABLE products (id SERIAL PRIMARY KEY, name TEXT, metadata JSONB DEFAULT '{}');

INSERT INTO products (name, metadata) VALUES
('Laptop', '{"brand":"Dell","specs":{"ram":16,"ssd":512},"tags":["electronics"]}');

-- Access: -> returns JSON, ->> returns TEXT
SELECT metadata->>'brand' AS brand,
    (metadata->'specs'->>'ram')::INT AS ram
FROM products;

-- Containment @> and key existence ?
SELECT * FROM products WHERE metadata @> '{"brand":"Dell"}';
SELECT * FROM products WHERE metadata ? 'brand';

-- Update JSON
UPDATE products SET metadata = metadata || '{"color":"silver"}' WHERE id=1;
UPDATE products SET metadata = metadata - 'color' WHERE id=1; -- remove key

-- MySQL JSON equivalent
UPDATE students SET preferences =
    '{"theme":"dark","notifications":true,"language":"en"}'
WHERE student_id = 1;
SELECT JSON_EXTRACT(preferences, '$.theme') AS theme FROM students;

-- GIN index for JSONB
CREATE INDEX idx_meta ON products USING GIN(metadata);

-- Build JSON from rows
SELECT jsonb_agg(jsonb_build_object('name',first_name,'salary',salary))
FROM employees WHERE dept_id = 1;

Full-Text Search¶

PostgreSQL has built-in full-text search — no need for ElasticSearch for basic use cases.

-- Basic search
SELECT * FROM articles
WHERE to_tsvector('english', title || ' ' || body)
    @@ to_tsquery('english', 'python & database');

-- Dedicated column + GIN index for performance
ALTER TABLE articles ADD COLUMN search_vec TSVECTOR;
UPDATE articles SET search_vec = to_tsvector('english', title || ' ' || COALESCE(body,''));
CREATE INDEX idx_search ON articles USING GIN(search_vec);

-- Search with ranking

FROM articles WHERE search_vec @@ to_tsquery('python & web')
ORDER BY rank DESC;

-- Auto-update trigger
CREATE TRIGGER trg_search BEFORE INSERT OR UPDATE ON articles
FOR EACH ROW EXECUTE FUNCTION
    tsvector_update_trigger(search_vec, 'pg_catalog.english', title, body);

Department Performance Analysis¶

WITH CourseStats AS (
    SELECT d.department_id, d.department_name,
        COUNT(DISTINCT c.course_id) AS course_count,
        COUNT(DISTINCT e.student_id) AS student_count,
        AVG(CASE
            WHEN e.grade='A+' THEN 10 WHEN e.grade='A' THEN 9
            WHEN e.grade='B+' THEN 8 WHEN e.grade='B' THEN 7 ELSE 5
        END) AS avg_grade
    FROM departments d
    LEFT JOIN courses c ON d.department_id = c.department_id
    LEFT JOIN enrollments e ON c.course_id = e.course_id
    GROUP BY d.department_id, d.department_name
)
SELECT department_name, course_count, student_count,
    ROUND(avg_grade, 2) AS avg_grade,
    CASE
        WHEN avg_grade >= 9.0 THEN 'Excellent'
        WHEN avg_grade >= 8.0 THEN 'Very Good'
        WHEN avg_grade >= 7.0 THEN 'Good'
        ELSE 'Needs Improvement'

FROM CourseStats ORDER BY avg_grade DESC;

);

    FROM employees

        RANK() OVER (ORDER BY AVG(e.salary) DESC) AS rn
    FROM employees e JOIN departments d ON e.dept_id = d.id
    GROUP BY d.name

Q5: Find consecutive login days (streak)¶

        login_date - (ROW_NUMBER() OVER (

    FROM user_logins

Section 1: SQL Fundamentals & Core Concepts¶

# Question Keywords Answer
1 What is SQL? SQL, Structured Query Language • Standard language for managing relational databases
• Create tables, insert/update/delete data, retrieve with SELECT
• Declarative — you say WHAT you want, not HOW
• Used by PostgreSQL, MySQL, Oracle, SQL Server
2 What is a database vs a schema? Database, schema • Database: entire collection of data + metadata
• Schema: namespace within a database grouping tables/views
• PostgreSQL: one DB can have multiple schemas
• Default schema is public
3 Categories of SQL commands (DDL, DML, DCL, TCL)? DDL, DML, DCL, TCL • DDL: CREATE, ALTER, DROP, TRUNCATE (structure)

• DCL: GRANT, REVOKE (permissions)
• TCL: COMMIT, ROLLBACK, SAVEPOINT (transactions)
4 DDL vs DML? DDL, DML, difference • DDL changes structure (schema) — auto-commits
• DML changes data (rows) — can be rolled back
• DDL: CREATE TABLE, ALTER TABLE, DROP TABLE
• DML: INSERT, UPDATE, DELETE, SELECT
5 DELETE vs TRUNCATE vs DROP? DELETE, TRUNCATE, DROP • DELETE: removes rows, can use WHERE, logged, fires triggers
• TRUNCATE: removes ALL rows, faster, resets identity, no triggers
• DROP: removes entire table (structure + data)
• DELETE is rollback-able; TRUNCATE in PG also rollback-able
6 WHERE vs HAVING? WHERE, HAVING, filter • WHERE: filters rows BEFORE grouping
• HAVING: filters groups AFTER GROUP BY
• WHERE cannot use aggregate functions
• HAVING without GROUP BY treats entire result as one group
7 CHAR vs VARCHAR? CHAR, VARCHAR, fixed • CHAR(n): fixed-length, padded with spaces
• VARCHAR(n): variable-length, no padding
• Use CHAR for fixed-size codes (country codes, hashes)
• In PG, VARCHAR without length = unlimited (same as TEXT)
8 Primary key vs unique key? PK, unique, constraint • PK: only one per table, no NULLs, main row identifier
• UNIQUE: multiple per table, allows one NULL
• Both enforce uniqueness and create an index
• PK has stronger semantic meaning
9 What is a foreign key? Foreign key, FK, referential • References a primary key in another table
• Enforces referential integrity
• Can be NULL (unless constrained), can have multiple FKs
• Actions: CASCADE, SET NULL, RESTRICT on delete/update
10 What is NULL? NULL, IS NULL, COALESCE • Represents unknown or missing data — NOT zero, NOT empty string
• Any comparison with NULL → NULL (not TRUE/FALSE)
• Check with IS NULL / IS NOT NULL
• COALESCE(col, default) replaces NULL
11 NULL vs empty string? NULL, empty string • NULL = absence of value; empty string = a value (zero-length text)
• NULL IS NULL → TRUE; '' IS NULL → FALSE
• LENGTH(NULL) → NULL; LENGTH('') → 0
• Test: IS NULL for NULL, = '' for empty string
12 UNION vs UNION ALL? UNION, UNION ALL • UNION: combines results, removes duplicates (slower)
• UNION ALL: combines results, keeps duplicates (faster)
• Both require same number and type of columns
• Use UNION ALL when duplicates are OK or impossible
13 SQL logical order of execution? Execution order, FROM • FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
• Can't use column aliases in WHERE (SELECT runs after)
• CAN use aliases in ORDER BY
• Understanding this explains many SQL behaviors
14 Why is execution order important? Execution order, aliases • Explains why aliases don't work in WHERE
• Explains why HAVING can use aggregates but WHERE can't
• Helps debug unexpected results
• Essential for writing correct complex queries
15 What is SQL injection? How to prevent? SQL injection, security • Attacker inserts malicious SQL through user input

16 OLTP vs OLAP? OLTP, OLAP, analytical • OLTP: operational — many short transactions, normalized, write-heavy
• OLAP: analytical — complex queries, denormalized, read-heavy

• Different table designs for each
17 Temporary table vs CTE vs view? Temp table, CTE, view • Temp table: persists for session, can be indexed
• CTE: exists for one query only, no DDL needed
• View: permanent named query, no data stored
• Temp table for large intermediate results; CTE for readability
18 IN vs EXISTS? IN, EXISTS, subquery • IN: checks if value is in a list or subquery result
• EXISTS: checks if subquery returns ANY rows
• EXISTS stops at first match (often faster for large subqueries)

19 COALESCE vs ISNULL/IFNULL? COALESCE, ISNULL • COALESCE(a, b, c): returns first non-NULL (SQL standard, any DB)
• ISNULL(a, b): SQL Server specific, only two args
• IFNULL(a, b): MySQL specific, only two args
• Always prefer COALESCE for portability
20 NULLIF function? NULLIF, division by zero • Returns NULL if two values are equal: NULLIF(a, b) → NULL if a=b
• Prevents division by zero: x / NULLIF(y, 0)
• Opposite-ish of COALESCE
• Useful for avoiding special-case values
21 CASE statement — simple vs searched? CASE, WHEN, conditional • Simple: CASE col WHEN 'A' THEN 'Active' END
• Searched: CASE WHEN salary > 100k THEN 'High' END
• Searched CASE is more flexible (any condition)
• Works in SELECT, WHERE, ORDER BY, GROUP BY
22 Division by zero handling? Division, zero, NULLIF • x / NULLIF(y, 0) — returns NULL instead of error
• CASE WHEN y != 0 THEN x/y ELSE 0 END
• PostgreSQL raises error on integer division by zero
• Always protect division with NULLIF or CASE
23 CAST vs :: in PostgreSQL? CAST, ::, type conversion • CAST(col AS INTEGER) — SQL standard, portable
• col::INTEGER — PostgreSQL shorthand
• Both do the same thing
• Use CAST for cross-database compatibility
24 Type coercion — implicit casting problems? Coercion, implicit cast • SQL auto-converts types in some cases (implicit cast)
• Can prevent index usage: WHERE int_col = '5'
• Can cause unexpected results with dates/numbers
• Always use explicit CAST for clarity
25 SELECT * vs specific columns? SELECT *, performance • SELECT * retrieves unnecessary columns (more I/O)
• Prevents covering index (index-only scan)
• Schema changes may break application code
• Always select only needed columns
26 DISTINCT vs GROUP BY for deduplication? DISTINCT, GROUP BY • Both remove duplicate rows
• DISTINCT: simpler syntax for basic dedup
• GROUP BY: needed when combining with aggregates
• Performance typically identical for simple cases
27 BETWEEN — inclusive? Gotchas with dates? BETWEEN, range, dates • BETWEEN is inclusive on both ends
• BETWEEN '2024-01-01' AND '2024-01-31' includes both
• With timestamps: BETWEEN '2024-01-01' AND '2024-01-31' misses Jan 31 after midnight

31 ORDER BY with NULLs? ORDER BY, NULLS FIRST, LAST • PG: NULLs sort last in ASC, first in DESC (default)

• ORDER BY col DESC NULLS LAST
• MySQL: NULLs sort first in ASC
32 SELECT INTO vs INSERT INTO ... SELECT? SELECT INTO, INSERT SELECT • SELECT INTO new_table FROM ... — creates new table with results
• INSERT INTO existing_table SELECT ... — inserts into existing
• SELECT INTO fails if table exists
• INSERT INTO SELECT preserves table structure
33 Correlated vs non-correlated subquery? Correlated, subquery • Non-correlated: runs once, independent of outer query
• Correlated: references outer query, runs per outer row

# Question Keywords Answer
1 INNER, LEFT, RIGHT, FULL OUTER JOIN? JOIN types, INNER, LEFT • INNER: only matching rows from both tables
• LEFT: all from left + matching right (NULLs if no match)
• RIGHT: all from right + matching left
• FULL OUTER: all from both tables
2 INNER JOIN vs LEFT JOIN — when to use? INNER, LEFT, choice • INNER: when you only want rows with matches in both tables
• LEFT: when you want ALL rows from left table regardless

• INNER is more restrictive
3 What is a CROSS JOIN? CROSS JOIN, cartesian • Produces cartesian product — every row × every row
• No join condition needed

• Also for comparing rows within same table

• Always use explicit JOIN syntax

• ON a.col = b.col — works with different column names
• USING produces one copy of the column in result
• ON is more flexible and explicit
8 What is a NATURAL JOIN? Why dangerous? NATURAL JOIN, auto • Automatically joins on all columns with same name

• Dangerous: columns may match unintentionally
• Avoid in production — use explicit JOIN ON

12 Join on multiple conditions? Multiple conditions, AND • FROM a JOIN b ON a.id = b.aid AND a.type = b.type

14 Joining more than two tables? Best order? Multiple tables, chain • Chain joins: FROM a JOIN b ON ... JOIN c ON ...

• Optimizer usually determines best physical order
• Write for readability; let optimizer handle order
15 Does join order affect performance? Join order, optimizer • Logical order (what you write) usually doesn't matter
• Optimizer rearranges joins for best plan
• Physical join order chosen by planner based on statistics
• Ensure table stats are up to date (ANALYZE)
16 Hash join vs nested loop vs merge join? Hash, nested loop, merge • Hash join: builds hash table on smaller table — O(n+m)
• Nested loop: for each row in outer, scan inner — good with index
• Merge join: both sides sorted, merge — O(n log n + m log m)
• Optimizer picks based on data size and indexes
17 Troubleshoot a slow join? Slow join, EXPLAIN • Run EXPLAIN ANALYZE — check join type and row estimates
• Add indexes on join columns
• Check for implicit type casting on join conditions
• Ensure table statistics are current (ANALYZE)
18 Join on different data types? Type mismatch, cast • Implicit casting may prevent index usage
• WHERE int_col = varchar_val → full scan
• Always match types: CAST(col AS INTEGER)
• Best practice: join columns should be same type
19 What is a LATERAL join? LATERAL, correlated FROM • Allows subquery in FROM to reference earlier tables

Section 13: Window Functions¶

# Question Keywords Answer
1 Window functions vs aggregate functions? Window, aggregate, differ • Aggregates collapse rows (GROUP BY); windows preserve them
• SUM(x) → one row per group; SUM(x) OVER() → every row
• Window adds computed column without reducing result set
• Can use both in same query
2 OVER() — empty vs with PARTITION BY? OVER, PARTITION BY, empty • OVER(): entire result set is one window
• OVER(PARTITION BY col): separate window per partition
• COUNT(*) OVER() → total count on every row
• COUNT(*) OVER(PARTITION BY dept) → per-dept count
3 PARTITION BY vs GROUP BY? PARTITION BY, GROUP BY • GROUP BY: collapses into one row per group
• PARTITION BY: keeps all rows, segments window calculation
• GROUP BY for summaries; PARTITION BY for per-row context
• Both create groups, different output shape
4 ORDER BY inside window function? ORDER BY, window • Defines the order for the window calculation
• Affects running computations: SUM() OVER (ORDER BY date) → running total
• Without ORDER BY: function sees entire partition
• With ORDER BY: default frame is UNBOUNDED PRECEDING to CURRENT ROW
5 ROW_NUMBER, RANK, DENSE_RANK — difference? ROW_NUMBER, RANK, DENSE_RANK • ROW_NUMBER(): unique sequential (1,2,3,4) — no ties
• RANK(): same rank for ties, skips (1,2,2,4)
• DENSE_RANK(): same rank for ties, no skip (1,2,2,3)
• Choice depends on how to handle ties
6 ROW_NUMBER for top-N per group? Top N, ROW_NUMBER • ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) rn
• Wrap in CTE: WHERE rn <= 3 → top 3 per dept
• Ensures exactly N rows per group
• Use DENSE_RANK if ties should all be included
7 ROW_NUMBER to remove duplicates? Dedup, ROW_NUMBER • WITH dups AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) rn FROM users) DELETE FROM users WHERE id IN (SELECT id FROM dups WHERE rn > 1)
• Keeps first (lowest id), deletes rest
• Change ORDER BY to pick which duplicate to keep
8 NTILE(n) for quartiles/percentiles? NTILE, quartile • NTILE(4) OVER (ORDER BY score) → quartiles (1-4)
• NTILE(100) → percentiles
• Divides rows into n equal-sized buckets
• Uneven rows: first buckets get one extra row
9 LAG() — compare to previous row? LAG, previous • LAG(salary, 1) OVER (ORDER BY date) — previous row's salary
• LAG(col, 2, default) — 2 rows back, with default if null
• Use for: month-over-month comparison, change detection
• Always specify ORDER BY
10 LEAD() — row-over-row growth? LEAD, next row, growth • LEAD(revenue, 1) OVER (ORDER BY month) — next month's revenue
• Growth: (LEAD(val) OVER (...) - val) / val * 100
• LEAD(col, 1, 0) OVER (...) — default to 0
• Opposite of LAG
11 FIRST_VALUE, LAST_VALUE — gotcha? FIRST_VALUE, LAST_VALUE • FIRST_VALUE(col): first value in frame
• LAST_VALUE(col): last value — gotcha: default frame ends at CURRENT ROW
• Fix: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
• Without fix, LAST_VALUE = current row
12 NTH_VALUE — when to use? NTH_VALUE, nth • NTH_VALUE(col, 3) OVER (ORDER BY col) — 3rd value
• Need explicit frame for reliable results
• Alternative: ROW_NUMBER() then filter
• Less commonly used than LAG/LEAD
13 Running totals with SUM() OVER()? Running total, SUM OVER • SUM(amount) OVER (ORDER BY date) — cumulative sum
• PARTITION BY dept ORDER BY date — per-dept running total
• Frame: UNBOUNDED PRECEDING to CURRENT ROW (default)
• Works with SUM, COUNT, AVG, etc.
14 Moving averages with windows? Moving average, ROWS BETWEEN • AVG(price) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) — 7-day MA
• ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING — centered MA
• Fixed-count window frame
• Essential for time-series analysis
15 Cumulative percentages? Cumulative pct, window • SUM(amount) OVER (ORDER BY amount DESC) / SUM(amount) OVER () * 100
• Running sum / total * 100
• Or use CUME_DIST() for rank-based cumulative distribution
• Pareto analysis (80/20 rule)
16 Window frame — ROWS BETWEEN options? ROWS BETWEEN, frame • UNBOUNDED PRECEDING — from start of partition
• N PRECEDING / N FOLLOWING — N rows before/after
• CURRENT ROW — current row
• UNBOUNDED FOLLOWING — to end of partition
17 ROWS vs RANGE in window frames? ROWS, RANGE, frame • ROWS: physical rows (exact count)
• RANGE: logical range based on ORDER BY value
• ROWS is more predictable and commonly used
• RANGE groups rows with same ORDER BY value
18 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW? Full frame, UNBOUNDED • Default frame when ORDER BY is specified
• Includes all rows from partition start to current
• Used for: running totals, cumulative sums
• Explicit declaration makes intent clear
19 ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING? Sliding window, centered • Centered window of 7 rows (3 before, current, 3 after)
• Used for: centered moving averages, smoothing
• Edge rows have smaller windows (partial)
• Frame size adapts at partition boundaries
20 Default frame when ORDER BY specified? Default frame, ORDER BY • RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
• Note: RANGE not ROWS — groups same-value rows together
• Without ORDER BY: entire partition is the frame
• Explicit ROWS BETWEEN is recommended for clarity
21 Multiple window functions in same query? Multiple windows, query • SELECT ROW_NUMBER() OVER w, SUM(x) OVER w FROM t WINDOW w AS (PARTITION BY dept ORDER BY salary)
• Each can have different OVER clause
• Named windows (WINDOW clause) reduce repetition
• Performance: optimizer shares sort
22 Named window — WINDOW w AS (...)? Named window, WINDOW • SELECT ... FROM t WINDOW w AS (PARTITION BY dept ORDER BY salary DESC)
• Reference: ROW_NUMBER() OVER w, SUM(x) OVER w
• Can extend: SUM(x) OVER (w ROWS BETWEEN ...)
• DRY — don't repeat partition/order
23 PERCENT_RANK and CUME_DIST? PERCENT_RANK, CUME_DIST • PERCENT_RANK(): (rank - 1) / (total - 1), range 0 to 1
• CUME_DIST(): fraction of rows ≤ current value
• PERCENT_RANK: first row always 0
• CUME_DIST: last row always 1
24 Find gaps in sequential data? Gaps, LEAD, sequence • SELECT id, LEAD(id) OVER (ORDER BY id) AS next_id FROM t WHERE LEAD(id) OVER (ORDER BY id) - id > 1
• Gap between current and next ID
• Or: generate_series LEFT JOIN approach
• Also: LAG to compare with previous
25 Find consecutive sequences (islands)? Islands, consecutive • Group consecutive rows: id - ROW_NUMBER() OVER (ORDER BY id) = constant for each island
• Called "gaps and islands" problem
• GROUP BY the computed constant to find each island
• Classic window function pattern
26 Time between events with windows? Time between, LAG • event_time - LAG(event_time) OVER (PARTITION BY user ORDER BY event_time) → interval
• Time since previous event per user
• AVG for average time between events
• NULL for first event (no previous)
27 FILTER with window functions? FILTER, window • COUNT(*) FILTER (WHERE status='active') OVER (PARTITION BY dept)
• Conditional window aggregation
• PG-specific (not widely supported)
• Alternative: SUM(CASE WHEN ... END) OVER (...)
28 DISTINCT with window functions? DISTINCT, window • No DISTINCT directly in window functions
• Workaround: CTE with DISTINCT, then apply window
• Or: DENSE_RANK to assign unique ranks
• Use subquery to deduplicate first
29 Window functions and performance? Window, performance • Sort-based: partition + order requires sorting
• Multiple windows with same sort share one sort
• Indexes on PARTITION BY + ORDER BY columns help
• Window functions scan data only once
30 Window functions in WHERE? Workaround? WHERE, window, CTE • Can NOT use window functions in WHERE clause
• Workaround: wrap in CTE/subquery, filter in outer
• WITH r AS (SELECT *, ROW_NUMBER() OVER (...) rn FROM t) SELECT * FROM r WHERE rn = 1
• This is why CTEs are essential
31 Rolling 7-day average of sales? Rolling average, 7 day • AVG(sales) OVER (ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
• 7 rows: 6 preceding + current
• Or RANGE: RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW
• ROWS for fixed count; RANGE for calendar days
32 Rank within partition, filter top-3 per group? Rank, partition, top 3 • DENSE_RANK() OVER (PARTITION BY category ORDER BY sales DESC) rk
• CTE + WHERE rk <= 3
• Includes ties (may return >3 per group)
• Use ROW_NUMBER for exactly 3
33 Year-over-year growth with windows? YoY, growth, LAG • LAG(revenue, 1) OVER (ORDER BY year) → previous year
• Growth: (revenue - LAG(revenue) OVER (...)) / LAG(revenue) OVER (...) * 100
• PARTITION BY product for per-product YoY
• Window approach is cleaner than self-join
34 SUM(x) OVER() vs SUM(x)? SUM OVER, aggregate, differ • SUM(x): requires GROUP BY, returns one row per group
• SUM(x) OVER(): no GROUP BY, adds total to every row
• Window: each row sees the total alongside its own values
• Useful for percentage calculations
35 First and last order per customer? First, last, per customer • FIRST_VALUE(order_date) OVER (PARTITION BY customer ORDER BY order_date ASC) → first
• LAST_VALUE(...) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) → last
• Or use MIN/MAX aggregate

# Question Keywords Answer
1 What is an index? How does it speed up queries? Index, B-Tree, speed • Data structure for fast row lookup (like a book's index)
• Avoids full table scan — jumps to matching rows
• Speeds up SELECT, slows INSERT/UPDATE/DELETE
• Most common: B-Tree (default)
2 B-Tree index — how it works? B-Tree, balanced tree • Sorted tree structure, O(log n) lookups

• UPDATE old + new index entries (if indexed column changes)
• DELETE marks index entries for cleanup
• Storage: each index uses disk space
5 Composite index — column order? Composite, multi-column, order • Index on (a, b, c) — column order matters
• Supports queries on: (a), (a,b), (a,b,c)
• Does NOT help queries on (b) or (c) alone
• Put most selective/most filtered column first
6 Leftmost prefix rule? Leftmost prefix, composite • Composite index (a, b, c) is like an index on a, (a,b), and (a,b,c)

7 Covering index (index-only scan) with INCLUDE? Covering, INCLUDE, index-only • Includes all columns needed → no table access

• INCLUDE columns not in index tree, just stored
8 Partial index — when useful? Partial index, filtered • CREATE INDEX idx ON orders(status) WHERE status = 'pending'
• Smaller index — only matching rows
• Perfect for: columns where you query specific values
• PG feature; not available in all databases
9 Expression (functional) index? Expression, functional index • CREATE INDEX idx ON t(LOWER(email)) — index on expression

10 Unique index vs unique constraint? Unique index, constraint • Unique constraint creates a unique index internally

• Both prevent duplicate values

11 Hash index — when over B-Tree? Hash index, equality • Hash index: only supports = (equality) lookups

15 Index selectivity — why low selectivity = useless? Selectivity, cardinality • Selectivity = fraction of distinct values in a column

16 Check if index is used? EXPLAIN ANALYZE? Index usage, EXPLAIN • EXPLAIN ANALYZE SELECT ... — shows actual execution plan
• Look for: Index Scan, Index Only Scan (good)
• Seq Scan (bad for large tables unless intended)
• Compare estimated vs actual rows
17 Seq scan vs index scan vs bitmap index scan? Seq scan, index scan, bitmap • Seq scan: reads every row (good for small tables or most rows)

20 CLUSTER — physical reorder by index? CLUSTER, physical order • CLUSTER table USING index — reorders table rows by index

• Exclusive lock during operation
• Big performance boost for range queries on clustered column
21 Find unused indexes? Unused index, pg_stat • SELECT * FROM pg_stat_user_indexes WHERE idx_scan = 0

22 Find missing indexes? Missing index, slow query • EXPLAIN ANALYZE shows Seq Scans on large tables

23 pg_stat_user_indexes for analysis? pg_stat_user_indexes • idx_scan: number of times index was used
• idx_tup_read: rows read from index
• idx_tup_fetch: rows fetched from table via index
• Low idx_scan = candidate for dropping
24 Choose between multiple indexes? Index choice, optimizer • Optimizer considers selectivity, cost, correlation
• Only one index per table used in simple queries
• Bitmap scan can combine multiple indexes
• Hint: check EXPLAIN to see which index was chosen
25 Indexes and NULL values? Index, NULL • B-Tree indexes include NULLs by default
• IS NULL queries CAN use B-Tree index
• Partial index: WHERE col IS NOT NULL excludes NULLs
• NULLs at the end/start of sorted index depending on ASC/DESC
26 CREATE INDEX CONCURRENTLY? CONCURRENTLY, no lock • CREATE INDEX CONCURRENTLY idx ON t(col) — no write lock

• Can fail (leaves invalid index — clean up with DROP)
• Essential for production databases
27 Optimize LIKE '%text%' (leading wildcard)? Leading wildcard, pg_trgm • Regular B-Tree can't help with leading wildcard

• Supports: LIKE '%text%', ILIKE, similarity
• Full-text search is alternative for word-based
28 pg_trgm for trigram-based indexing? pg_trgm, trigram, similarity • CREATE EXTENSION pg_trgm

• SELECT * FROM t WHERE col % 'search_term'

• Expression: CREATE INDEX idx ON t((col->>'specific_key'))
• Choose based on query patterns
30 Impact of indexes on INSERT/UPDATE/DELETE? Index, write, DML • Each index adds write overhead

• UPDATE: delete old + insert new (if indexed column changes)
• Unused indexes: pure overhead — drop them

# Question Keywords Answer
1 What is a transaction? Why important? Transaction, unit of work • Unit of work that is all-or-nothing
• BEGIN; ...statements...; COMMIT; or ROLLBACK;

• Groups related operations into atomic unit
2 ACID properties with examples? ACID, Atomicity, Consistency • Atomicity: all or nothing (transfer = debit + credit)

• ROLLBACK: undoes all changes since BEGIN

• After ROLLBACK: database returns to prior state

• SAVEPOINT sp1; ... ROLLBACK TO sp1; — partial undo
• Transaction continues after partial rollback
• Multiple savepoints allowed

• READ COMMITTED: prevents dirty reads (PG default)
• REPEATABLE READ: prevents non-repeatable reads
• SERIALIZABLE: prevents all anomalies

• Prevented by READ COMMITTED and above
• Not possible in PostgreSQL
7 Non-repeatable read? Non-repeatable read, repeat • Same query returns different data within same transaction
• Another transaction modified rows between reads
• Prevented by REPEATABLE READ
• PG default (READ COMMITTED) allows this

• Different statements in same transaction may see different snapshots

# Question Keywords Answer
1 MVCC — how PostgreSQL implements it? MVCC, multi-version • Each transaction sees a snapshot of data at a point in time
• Rows have xmin/xmax (creation/deletion transaction IDs)
• Readers don't block writers; writers don't block readers
• Old versions kept until VACUUM cleans them
2 Why doesn't PG block readers for writers? MVCC, no reader block • MVCC gives each reader its own snapshot
• Writer creates new version; reader sees old version

• Key advantage of MVCC architecture
3 Shared lock vs exclusive lock? Shared, exclusive, lock • Shared: multiple readers can hold simultaneously (read lock)
• Exclusive: only one holder, blocks all others (write lock)

4 Row-level vs table-level locking? Row lock, table lock • Row-level: locks specific rows (most common in PG)
• Table-level: locks entire table (ALTER TABLE, LOCK TABLE)
• PG prefers row-level for concurrency
• Table locks needed for DDL operations
5 SELECT FOR UPDATE — when and why? FOR UPDATE, row lock • Locks selected rows until COMMIT/ROLLBACK
• Prevents other transactions from modifying them
• SELECT * FROM orders WHERE id = 1 FOR UPDATE
• Use for: read-then-update patterns, reservations
6 SELECT FOR SHARE? FOR SHARE, shared lock • Prevents other transactions from updating/deleting
• Allows other SELECT FOR SHARE
• Weaker than FOR UPDATE (still allows reads)
• Use when you need to ensure data doesn't change
7 NOWAIT — can't acquire lock? NOWAIT, lock timeout • SELECT FOR UPDATE NOWAIT — error immediately if locked
• Instead of waiting indefinitely
• Application handles error (retry or fail)
• Better UX than hanging on locked rows
8 SKIP LOCKED — job queues? SKIP LOCKED, queue • SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1 — skip locked rows
• Multiple workers can process different jobs concurrently
• Locked rows are invisible — worker gets next available
• Perfect for: task queues, work distribution
9 Deadlock — prevention strategies? Deadlock, prevention • Two transactions hold locks each other needs
• Prevention: always acquire locks in consistent order
• Keep transactions short — less chance of conflict
• PG auto-detects and kills one transaction
10 PG deadlock detection and resolution? Deadlock, detection • PG checks for deadlocks every deadlock_timeout (1s default)
• Detects cycle in lock wait graph
• Kills one transaction with least work done
• Application should retry killed transaction
11 Lock timeout configuration? lock_timeout, config • SET lock_timeout = '5s' — fail after 5 seconds
• Prevents indefinite waits
• statement_timeout for overall query timeout
• Set per-session or per-transaction
12 Advisory locks vs regular locks? Advisory, regular, difference • Regular: automatic, tied to table/row operations
• Advisory: manual, application-controlled
• Regular: released at transaction/statement end
• Advisory: session-level (or transaction with _xact variant)
13 Diagnose locking issues? pg_locks, pg_stat_activity • pg_locks — shows all active locks
• pg_stat_activity — shows waiting queries
• pg_blocking_pids(pid) — who blocks whom
• Join both for complete picture
14 Optimistic vs pessimistic locking — implementation? Optimistic, pessimistic, how • Pessimistic: SELECT ... FOR UPDATE; UPDATE ...;
• Optimistic: add version column, UPDATE ... WHERE version = expected; CHECK rows_affected > 0
• Pessimistic: simpler, blocks concurrent access
• Optimistic: better throughput, retry on conflict
15 Lock escalation — does PG do it? Lock escalation, PG • Lock escalation: upgrading many row locks to table lock
• PostgreSQL does NOT do lock escalation
• Always row-level locks regardless of count
• Other DBs (SQL Server) may escalate
16 Locking impact on concurrent writes? Concurrent, write, lock • Row-level locks: minimal blocking (only same rows)

• Different rows: fully concurrent

17 Job queue with SKIP LOCKED? Queue, SKIP LOCKED, worker • BEGIN; SELECT id FROM jobs WHERE status='pending' FOR UPDATE SKIP LOCKED LIMIT 1; UPDATE jobs SET status='processing' WHERE id = ?; COMMIT;

• No coordinator needed
• Simple and effective
18 Lock contention on hot rows? Hot row, contention • Frequently-updated row (counter, balance) creates bottleneck

• Or denormalize — spread updates across rows
19 Table-level lock modes? ACCESS SHARE, ROW EXCLUSIVE • ACCESS SHARE: SELECT (weakest)
